# Phone remote

Start the local app with `Open Intel exercises.command` (an Intel camera is not
required for phone control). On the laptop select **Connect a phone**, then scan
the code using a phone on the same Wi-Fi. Choose the operated leg and operation
date on the laptop first. The remote lists the current programme week's exercises.

The phone opens a remote controller, not a second exercise or camera session.
An exercise choice opens the laptop demonstration. **Ready to exercise** continues
from that demonstration; **Start** begins the laptop countdown. Pause/resume,
finish, cancellation of countdown and voice controls are available in their relevant
states. Pausing pauses MediaRecorder and live processing, excluding paused wall
time from the session clock. The laptop also has a Pause/Resume button.

The localhost service creates a separate listener on port 8892 only when pairing
is requested. That listener serves only phone.html, phone-remote.mjs and the two
token-protected remote endpoints, not files or Intel camera APIs. Pairing expires
in 30 minutes, on laptop page closure or explicit disconnection. Only one pairing
is active. Commands require a fresh laptop heartbeat; controls disable on connection
loss. The phone receives exercise names and session/control state, not patient
identifiers or camera images. This is same-network HTTP pairing, not an encrypted
internet relay. Do not expose port 8892 to the internet.

GitHub Pages can serve the remote interface but cannot run the Python pairing
service. Pairing codes must be generated by the local laptop app. Public phone.html
without a pairing code displays connection instructions. Browser reload of the
phone requires scanning again because the token is held in memory, not storage.

Automated checks use separate laptop/phone browser pages. Actual handset and
Wi-Fi firewall behaviour still need testing on the target network.
